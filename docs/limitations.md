# SecureVOTE — System Limitations & Security Boundaries

## Research-Oriented Prototype Notice
SecureVOTE is a **research-oriented prototype** designed for academic and pedagogical evaluation of embedded voting integrity concepts. It is not an election-ready, nationally deployable, or legally certified system. It demonstrates how cryptographic integrity verification, tamper-evident logging, and defense-in-depth mechanisms can be implemented on low-cost microcontrollers and audited independently.

---

## Technical & Architectural Limitations

### 1. Plaintext UART Communication (No Transport Encryption)
- **Direct Serial Channel**: Communication between the Arduino Uno microcontroller and the serial bridge occurs over raw asynchronous serial UART (9600 baud, 8-N-1).
- **Absence of Link Encryption**: The UART link does not implement hardware-level TLS, AES-GCM, or link-layer encryption. An attacker with physical access to the UART RX/TX lines can eavesdrop on ballot transmissions.
- **Architectural Boundary**: In production voting systems, point-to-point connections require dedicated cryptographically authenticated buses or optical air-gapped physical interfaces. In SecureVOTE, sequence counter enforcement and backend integrity verification detect message replay and insertion, but payload privacy over the physical wire relies on physical booth security.

---

### 2. Demo-Mode Synthetic Session Authentication
- **Fail-Closed Default**: In standard operation, the serial bridge enforces strict fail-closed authorization: any vote record lacking a valid `session_token` issued by the backend is rejected with `HTTP 401 Unauthorized`.
- **Demo-Mode Fallback**: When the `--demo-mode` CLI flag is explicitly enabled, the bridge generates synthetic credentials (`VOTER-SERIAL-{device_id}-{seq}`) solely for automated local test scenarios and bench demonstrations.
- **Audit Logging**: All synthetic session creation events are explicitly marked with `[DEMO-MODE]` tags in logs to ensure they are never confused with authenticated voter participation.

---

### 3. Simulated Credential / Session Authorization (RFID Fallback)
In commercial electronic voting systems, voter authentication is frequently coordinated through physical smart cards or RFID tokens. In this prototype:
- **Pin & Resource Constraints**: The Arduino Uno (ATmega328P) has only 14 digital I/O pins and 2048 bytes of SRAM. Allocating pins for a 20x4 I2C LCD, 4 candidate buttons, Confirm button, Admin button, Tamper switch, Status LEDs, and Buzzer exhausts available digital and analog pins.
- **Simulation Stability**: Software simulation of SPI-based RFID readers (e.g. MFRC522) in browser-based Wokwi environments exhibits known timing and synchronization edge cases.
- **Design Decision**: Voter credentials and session tokens (`session_token`) are managed as simulated credential/session authorization tokens generated by the backend API and relayed via the serial bridge. This cleanly decouples voter authentication from ballot casting without compromising system auditability.

---

### 4. Microcontroller Cryptographic Boundaries
- The 8-bit ATmega328P clocked at 16 MHz with 2 KB SRAM cannot perform asymmetric public-key cryptography (e.g., RSA-2048 or Ed25519) within acceptable user latency or memory budgets.
- **Architectural Boundary**: Microcontroller firmware computes CRC16 and fast checksums for configuration validation. Full cryptographic integrity verification (SHA-256 hash chains, HMACs, and digital signatures) is enforced upstream at the backend service layer.

---

### 5. Wokwi Simulation Environment & CLI Token
- The Wokwi simulation diagram (`simulation/diagram.json`) and configuration (`simulation/wokwi.toml`) are validated and linted (`wokwi-cli lint`).
- Executing automated headless simulations via `wokwi-cli` requires an active personal user token (`WOKWI_CLI_TOKEN`) from Wokwi Cloud.
- For interactive visual inspection and testing, users can load `diagram.json` and `.pio/build/uno/firmware.hex` directly into the web simulator at [wokwi.com](https://wokwi.com).

---

### 6. Dashboard JWT Storage Strategy & Client-Side Weaknesses
- **Token Delivery**: The FastAPI backend is a pure REST JSON API (`POST /api/auth/login`) that returns signed JWT tokens directly in the response body rather than setting `httpOnly` secure cookies.
- **Client Storage Mechanism**: The dashboard manages active authentication state in memory via React Context (`AuthContext`), with fallback persistence in browser `localStorage` for prototype convenience across tab navigation and reloads.
- **Known Prototype Weakness**: In production election and administrative consoles, storing access tokens in `localStorage` exposes them to potential exfiltration if a Cross-Site Scripting (XSS) vulnerability exists. Production systems should enforce secure `httpOnly`, `SameSite=Strict` cookies or dedicated backend session proxies.
- **Fail-Closed 401 Session Interceptor**: When any API request receives an `HTTP 401 Unauthorized` (such as an expired token or invalid signature), the frontend client immediately clears all in-memory and local session data, wipes cached credentials, and cleanly redirects the operator to `/login` to avoid silently broken or corrupted operational states.
